# Bundled linters

What each image ships, one row per tool. There are three images:

- **`linterpol`** (lean): linters that ship as static binaries, for the common stack.
- **`linterpol-jvm`** (JVM sibling): a JRE plus JVM-language linters. A separate image, not part of
  `linterpol`, so the lean image's consumers don't carry a JRE they don't need.
- **`linterpol-dotnet`** (.NET sibling): the .NET runtime plus C# linters (CSharpier). A separate
  image for the same reason as the JVM sibling, so the lean image's consumers don't carry a .NET
  runtime they don't need.

> **Generated.** The tables below are produced from the per-image Dockerfiles
> (`images/<variant>/Dockerfile`) by [`gen-linters.sh`](./scripts/gen-linters.sh), which CI runs on
> any Dockerfile change (`regen-linters.yml`) and commits back. Don't hand-edit or commit them:
> change the Dockerfile (the `FROM` line and its `# linter:` annotation); run
> `./scripts/gen-linters.sh` locally to preview.

## Adding a linter

First pick the image: a linter for the common stack goes in the lean image
(`images/lean/Dockerfile`); a JVM-language linter that needs a JRE goes in the jvm image
(`images/jvm/Dockerfile`); a C# linter that needs the .NET runtime goes in the dotnet image
(`images/dotnet/Dockerfile`). A brand-new stack gets its own `images/<variant>/Dockerfile` plus a
`linters:<variant>` section here. Then:

**Lane 1 (a static Go/Rust/Haskell binary with an official image)** is the cheap path:

1. Add the stage with its annotation: a `# linter: lints: <what> | repo: <url>` line, then
   `FROM <official-image>:<tag>@<digest> AS <name>`.
2. Add a copy: `COPY --from=<name> <path-in-image> /usr/local/bin/<name>`.
3. That's it. CI regenerates the table above on the Dockerfile change; run `./scripts/gen-linters.sh` locally to preview.

Confirm the upstream image ships both `linux/arm64` and `linux/amd64` first, so the
combined image stays multi-arch:

```bash
docker manifest inspect <official-image>:<tag> | grep -i architecture
```

**Lane 2 (npm/pip/apt tool, or a downloaded binary)** goes in an install block or a
download-and-verify stage in the variant's Dockerfile, with a self-contained annotation that carries
its own name and version:

```dockerfile
# linter: tool: <name> | version: <x.y.z> | lane: 2 | lints: <what> | repo: <url>
```

For a downloaded binary, drop `version:` and put the version in an `ARG <NAME>_VERSION=` line below
the annotation, so it stays the single source of truth and Renovate can bump it. CI then regenerates
the table (run `./scripts/gen-linters.sh` locally to preview). If Lane 2 ever grows to many
heterogeneous tools, that's the cue to switch its runner to [pre-commit](https://pre-commit.com).
